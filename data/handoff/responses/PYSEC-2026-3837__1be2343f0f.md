# Annotated tag came back containing a local file

Our release job creates an annotated tag for a caller-supplied revision. That revision is supposed to name a commit, and we pass our own release note as the tag message. The tag that came back was annotated, but its message was the full contents of a file on the build machine. We had not asked for the message to be taken from disk. The revision string was the only caller-supplied part of the call.

The same disclosure happened when a caller sent that kind of string as the tag's name. Supplying the file-reading value as an extra keyword, rather than as the revision or the name, did the same thing.

## Impact

Anyone who can choose that string can read a local file and get its contents back in the tag message, with the privileges of this process. A caller-supplied revision must not select a file and return the contents. An extra option forwarded with a revision or with a comparison must not select a file and return the contents either.

## What must keep working

- Creating an annotated tag with our own message, aimed at an ordinary commit such as the current head or a branch name, still stores that message and still points at that commit.
- Creating a lightweight tag with no message still produces a tag that carries no annotation.
- Asking to replace an existing tag still moves that tag onto the commit we name.
- Blaming a file that is already in the repository, both as a full blame and as the incremental stream, still returns that file's lines for an ordinary commit.
- Diffing one commit against another, and diffing the index against a commit, still reports the change. A search for a line that was added or removed still finds that change. That search reads the commits being compared, not a separate file.
