# Mechanisms covered and changed (packages/client/src/client/auth.ts)

1. `fetchToken()` read `provider.clientInformation()` with no SEP-2352 issuer-stamp check, so a provider pinned with `expectedIssuer` (ClientCredentialsProvider, CrossAppAccessProvider) sent its client_secret to whatever authorization server the caller passed. It now resolves the target issuer (`metadata.issuer`, or the AS URL when there is no metadata) and throws `AuthorizationServerMismatchError` on a mismatched stamp before `prepareTokenRequest`, `codeVerifier` or any request. **Pointed to by the report** (it names `fetchToken()`, the client-credentials provider and `expectedIssuer`).
2. Credentials presented through `addClientAuthentication` (PrivateKeyJwtProvider, StaticPrivateKeyJwtProvider: `client_assertion`) went through the same unchecked `fetchToken` path. The same check now covers them, and in `executeTokenRequest` it runs before `addClientAuthentication` is ever called. **Partly from the report** ("whichever of the SDK's OAuth client functions", "credentials configured on a provider"); I identified the assertion path specifically **by reading the code**.
3. `executeTokenRequest()`, the shared token-request choke point for `exchangeAuthorization()`, `refreshAuthorization()`, `fetchToken()` and `auth()`, now refuses `clientInformation` whose `issuer` stamp names a different AS than the one being called. This covers saved (DCR, CIMD or static) client credentials and the refresh token or authorization code sent alongside them, whichever low-level function is used. **Pointed to by the report's wording** ("whichever of the SDK's OAuth client functions", "credentials the application saved from an earlier sign-in"); the choke point itself was **found by reading the code**.
4. `startAuthorization()` now refuses stamped client information for a different AS, so a client_id from one AS is never presented at another AS's authorization endpoint. **Found by reading the code** (it follows from the report's general "never presented to a different AS" rule).
5. `auth()` read client information for its own stamp check and then re-read it inside `fetchToken()`. A provider whose read does not return what `saveClientInformation` just stored could still send the old AS's secret. Mechanism 3 now catches that re-read. **Found by reading the code.**
6. In `auth()`, an unstamped token set was back-stamped to the AS resolved now, even when the stored client information was stamped for a different AS. A typical case is a provider that round-trips the client-info stamp but stores tokens through the wire schema, which strips `issuer`. The A-issued refresh_token was then POSTed to the attacker's AS. Such tokens are now treated as belonging to the client's AS and discarded, so there is no back-stamp and no refresh, and the flow signs in afresh at the new AS. **Partly from the report** ("credentials the application saved from an earlier sign-in there, however that sign-in was done"); the concrete mechanism was **found by reading the code**.

Legitimate behaviour preserved: unstamped or legacy credentials and providers built without `expectedIssuer` are not restricted, and legacy storage is still back-stamped. One trailing-slash difference is tolerated, as in `issuersMatch`. A move to a new AS still re-registers or uses CIMD and signs in there. Matching issuers proceed unchanged.

Not changed: the raw-string helpers in `crossAppAccess.ts` (`exchangeJwtAuthGrant` and `requestJwtAuthorizationGrant`) carry no issuer stamp, so there is nothing to bind. A bare `refreshToken` string given to `refreshAuthorization` alongside unstamped client info cannot be bound either. The `skipIssuerMetadataValidation` opt-out still trusts `metadata.issuer` as documented.
